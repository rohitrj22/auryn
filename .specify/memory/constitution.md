# Auryn Constitution

Auryn is a graph-native memory engine for AI agents, built on FalkorDB.
It is the submission for Track 02, Agent Memory and Coordination, of the
WeMakeDevs "Graph Hacks: Context for AI Agents" hackathon.

## Core Principles

### I. Graph-Native Memory (NON-NEGOTIABLE)

FalkorDB MUST be the primary graph database and MUST perform the memory work
itself. Memory state MUST NOT be duplicated in a second store that could serve
the same reads.

The acceptance check is destructive and MUST pass: stop the FalkorDB container,
then run the demo. The product MUST fail. If the product still answers from
memory, the graph is decoration and the principle is violated.

Rationale: hackathon rule 3 disqualifies a graph drawn on top of ordinary
storage. This principle makes that rule a test we can run, not an opinion.

### II. The Five Criteria Are the Deliverable (NON-NEGOTIABLE)

Track 02 names five judging criteria. Each one MUST ship with a command a
judge can run, and the README MUST name that command.

| Criterion | Required proof |
|---|---|
| Episodic, semantic, procedural memory | Three distinct node labels, written and recalled separately |
| Persistent conversation history | Kill the process. Restart with an empty prompt. The agent still knows. |
| Shared state and handoffs between agents | Agent B reads nodes agent A wrote. No message passes between them. |
| High-concurrency reads and writes | A benchmark that reports measured operations per second |
| Separate memory per user or tenant | One FalkorDB graph per tenant. A cross-tenant read MUST return nothing. |

No feature outside this table may be built while any row lacks its proof.

Rationale: the prize goes to the best entry against these five bullets. Work
that does not move a row does not move the result.

### III. Domain-Agnostic Engine, Replaceable Demo

The engine package MUST contain no business vocabulary. Its node labels and
its public functions MUST stay generic, for example `Tenant`, `Session`,
`Event`, `Fact`, `Procedure`, `Agent`, `Handoff`.

The support-crew demo MUST depend on the engine, and the engine MUST NOT
depend on the demo. The demo MUST stay thin, and SHOULD stay under 20% of
project source lines.

The acceptance check: a reviewer greps the engine package for support-domain
words such as `ticket`, `refund`, or `order`. Zero hits are required.

Rationale: the engine is the product and the demo is its proof. Mixing them
makes the generality claim unverifiable.

### IV. A Judge Runs It With Zero Credentials

The repository MUST run end to end with no API key. A `mock` model provider
is the default. It MUST exercise every graph read and write path.

When `GEMINI_API_KEY` is present, the provider MUST switch to
`gemini-3.8-flash` without any code change. The provider boundary MUST be a
single small interface.

The acceptance check: in a clean clone with no `.env`, the documented quickstart
MUST reach a working demo.

Rationale: rule 10 asks for complete local setup instructions. A judge who
cannot run the project scores what they cannot see.

### V. Secrets and Data Hygiene (NON-NEGOTIABLE)

No credential may enter the repository, the README, the commit history, or the
demo video. `.env` MUST stay in `.gitignore`.

Work credentials and work gateways MUST NOT be used. This is a personal entry
with a public repository.

Data MUST be public, synthetic, or the author's own. The demo dataset MUST be
synthetic and MUST be generated by committed code, so a judge can regenerate it.

The acceptance check: scan the full history for key patterns before the repo
goes public. Any hit blocks the submission.

Rationale: rule 6 forbids restricted data. A leaked key is worse than a lost
prize.

### VI. Submission Completeness Is a Build Gate

Rule 10 lists six required artifacts. Each one MUST exist before the deadline:

1. A public source-code repository.
2. A README stating the setup steps and the graph data model.
3. The Cypher queries and graph algorithms the product depends on, documented.
4. A demo video of the working project.
5. A live deployment, or complete local setup instructions.
6. The track named explicitly, plus a disclosure of AI assistant use.

A missing artifact MUST be treated as a build failure, equal in weight to a
failing test.

Rationale: a strong project with no video scores nothing. These artifacts are
part of the product, not paperwork after it.

### VII. Ship The Demo (Deadline Discipline)

The deadline is 2026-10-18 23:59 IST and it does not move. Depth on the five
criteria MUST beat breadth of features.

Rules that follow from this:

- Any work that does not serve a row in Principle II is out of scope.
- A feature that is not in the demo video SHOULD NOT be built.
- MCP exposure, extra domains, and a second demo are explicitly deferred. They
  may be built only after every Principle II row has passing proof and the
  video is recorded.
- When a choice appears between a correct design and a shippable one, take the
  shippable one and record the trade-off in the README.

Rationale: an unfinished excellent design loses to a finished good one.

## Technology and Data Constraints

The stack is fixed. Changing any row requires an amendment.

| Concern | Decision | Reason |
|---|---|---|
| Graph database | FalkorDB, via Docker | Required by rule 2 |
| Language | Python 3.14 | Installed; `node` is absent on this machine |
| Package manager | `uv` | Installed and fast |
| Model provider | `mock` default, `gemini-3.8-flash` when keyed | Verified HTTP 200 on 2026-10-18 |
| Retired models | `gemini-2.5-flash` MUST NOT be used | The API returns 404 for new keys |
| Secrets | `.env`, mode 600, git-ignored | Principle V |

Two implementation traps are already known and MUST be handled:

1. `gemini-3.8-flash` spends output budget on thinking tokens. A low
   `maxOutputTokens` returns empty text. Set a generous cap, or disable
   thinking explicitly.
2. Cross-tenant isolation relies on one graph per tenant, not on a filter in a
   `WHERE` clause. A filter is a bug, not an implementation.

## Development Workflow and Quality Gates

Spec-driven development governs this project. The order is
constitution, specify, clarify, plan, tasks, implement. A later stage MUST NOT
start before its predecessor is written.

Testing is scoped to the deadline. Every Principle II row MUST have an
automated check that a judge can run with one command. Tests beyond those rows
are optional.

Time checkpoints, in IST. A missed checkpoint triggers a cut in scope, never a
slip of the deadline.

| Time | Gate |
|---|---|
| 15:00 | Engine writes and reads all three memory types in FalkorDB |
| 18:00 | Demo crew runs, and the restart proof passes |
| 20:00 | Concurrency benchmark and tenant isolation checks pass |
| 21:00 | README complete, with the graph model and the Cypher queries |
| 22:00 | Demo video recorded |
| 23:00 | Submitted, leaving one hour of buffer |

## Governance

This constitution supersedes any other practice or preference for this project.
When guidance conflicts, this document wins.

Amendments require three things: a written reason, a version bump under the
policy below, and an update to any stage artifact the change invalidates.

Versioning policy:

- MAJOR: a principle is removed or redefined in a backward-incompatible way.
- MINOR: a principle or section is added, or guidance expands materially.
- PATCH: wording, typos, and clarifications that do not change meaning.

Compliance review: before the 21:00 IST README gate, walk Principles I, II, III
and V and run each stated acceptance check. Record the result in the README.
A principle marked NON-NEGOTIABLE MUST NOT be waived. The remaining principles
may be traded off only under Principle VII, and only with the trade-off written
down.
